\chapter{Introduction}
\label{ch:intro}

This manual is about using LibreILA. It contains a worked example of a capture on hardware, modifying the core, wiring into the design, driving it from either host, reading back what it captured, using the GUI and some basic troubleshooting. Although care is taken to write every minor detail down, it is assumed that the reader is familiar with using FPGA toolchains, the command line, and a serial terminal. 


\section{What LibreILA is}
\label{sec:intro_what}

LibreILA is an in-system logic analyzer: a small core spliced into a link inside the FPGA fabric, which watches that link go past and records it. Any net in the RTL can be probed. While armed it writes one sample of the probed signals into a circular buffer in fabric RAM on every sampling clock edge, so the buffer always holds the most recent window of history. Once a condition specified by the user is met, the core stops writing and the buffer is frozen after specified post-trigger samples. The user can then read the buffer back into a VCD file on the host, and open it in a waveform viewer to see what happened.

The splice is pass-through. The core's two probe ports are shorted combinationally, so the link it sits in the middle of behaves exactly as it did before and pays no latency for being watched. The two mirrored ports allow easy connection when using GUI based design tools.

\section{Using LibreILA}
\label{sec:intro_deliverables}

The core is delivered two ways, and which one you build decides which host drives it and which chapters of this manual you need.

\texttt{libre\_ila} is the core itself, with an AXI4Lite slave port. It suits a design that already carries a bus master: a hard or soft processor, or anything else that can write registers. The baremetal C driver under \texttt{drivers/baremetal/} drives it from firmware, so a capture never leaves the chip and no PC has to be attached to take one. Chapter~\ref{ch:cdriver} covers that path on its own, end to end.

\texttt{libre\_ila\_uart} wraps the same core with a UART and a packet parser, putting the register map at the end of two wires instead of on a bus. Nothing inside the core changes. It suits a design with no bus master to spare, or a board you would rather drive from a laptop. The python driver under \texttt{drivers/python/} drives it from a PC, either from the command line (Chapter~\ref{ch:cli}) or from a window (Chapter~\ref{ch:gui}). This makes the usage very similar to a commercial logic analyzer.

Everything on either side of that choice is shared. Both builds come out of the same generator and are wired into a design the same way, and both capture into the same buffer and are read back into the same VCD. Table~\ref{tab:intro_paths} is the short version.

The remaining chapters serve both. Chapter~\ref{ch:stack} describes how the python driver is put together, for a reader scripting against it rather than using the front ends. Chapter~\ref{ch:trouble} is the symptom-to-fix list, and Appendix~\ref{app:nohw} runs the test suite with no hardware attached. If you are here for the first time, start with Chapter~\ref{ch:started} whichever build you are eventually after: it takes a capture on a stock build with the wiring already done, so the pieces have names before you have to choose between them.

Interestingly enough, the \texttt{libre\_ila\_uart} build is simply a \texttt{libre\_ila} core with a \ac{UART} to AXI4Lite bridge around it. If end user demands more speed, HDMI, USB or Ethernet bridges could be added in the same way.

\section{Conventions}
\label{sec:intro_conventions}

Table~\ref{tab:intro_conventions} lists the conventions this manual holds to throughout.

\begin{table}[H]
    \centering
    \begin{tabularx}{\textwidth}{|l|X|}
        \hline
        \rowcolor{gray!40} \textbf{Written as} & \textbf{Means} \\
        \hline
        \texttt{make sim} & A command, shown without a shell prompt so it can be copied whole. Unless the text says otherwise it is run from the root of your clone \\
        \hline
        \texttt{\{repo\}} & The root of your clone, wherever you put it. Every other path is relative to it, as in \texttt{drivers/python/libre\_ila.py} \\
        \hline
        TRIG\_CFG & A register or one of its fields, spelt as the datasheet register map spells it \\
        \hline
        \texttt{G\_SAMP\_BUFF\_DEPTH} & A generic, fixed at synthesis and set in \texttt{configuration.csv} \\
        \hline
        \hline
        \texttt{0b001x1} & A trigger pattern, where \texttt{x} is a bit that is not compared \\
        \hline
        bit 0 & The least significant bit, and the first signal listed in \texttt{portmap.csv}. Bit order is counted that way everywhere \\
        \hline
    \end{tabularx}
    \caption{Conventions used in this manual.}
    \label{tab:intro_conventions}
\end{table}

Two names are kept apart deliberately. \emph{The C driver} always means the baremetal driver for \texttt{libre\_ila} and \emph{the python driver} always means the host driver for \texttt{libre\_ila\_uart}; neither is ever called just ``the driver'', because the two share a register map and nothing else.
